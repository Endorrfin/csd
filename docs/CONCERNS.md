Перед списком проблем — те, що працює і що варто **вміти розповісти**:

| | Чому це сильно |
|---|---|
| **`.github/dependabot.yml`** — не дефолтний, а осмислений: групування по областях, `open-pull-requests-limit`, **мажори вимкнені навмисно** (перший прогін дав 16 одночасних мажорних PR — це не черга рев'ю, це шум) | Це готова відповідь на питання «як ви контролюєте оновлення бібліотек» |

Тепер це regression-тест у CI |

| **e2e з Testcontainers** (`postgres:16-alpine`) — реальна БД, реальні міграції | Ловить те, що моки не ловлять принципово |
| **Smoke-тест фронтенду грепає `ng-server-context`**, а не `<app-root>` | Літеральний тег матчив CSR-шелл і проходив би саме тоді, коли SSR зламався |
| **Умовний `migration:run`** — міграції не крутяться, якщо `migration:show` не показав pending | Плюс `check:cjs` **перед** міграціями: ніколи не мутувати прод-RDS заради збірки, яка не піднімається |
| **`test.yml` — три паралельні джоби (`backend`, `ui`, `e2e`) без `paths:`-фільтрів** | Кожна джоба ганяє рівно ланцюг `verify` свого застосунку, тому зелений PR означає те саме, що зелений локальний `verify`. `paths:`-фільтр навмисно не додано: пропущена джоба не репортить статус і підвісила б PR, якби ці перевірки зробили required |
| **Статична concurrency-група `deploy-prod` з `cancel-in-progress: false`** | Мерж і ручний `workflow_dispatch` серіалізуються в одну чергу, і жоден деплой не переривається на півдорозі. Раніше `github.event_name` у назві групи розводив їх у **різні** групи — два `migration:run` могли піти на одну базу одночасно |
| **Інваріант «SSR не ходить по HTTP за власні статичні асети»** (`ARCHITECTURE.md` §8.3) | Написаний після реального інциденту: `provideTranslateHttpLoader` під час SSR робив справжній мережевий запит за `/assets/i18n/ua.json`, а `HttpErrorResponse` з голого `.subscribe()` вилітав повз `catch(next)` у `server.ts` — Node вбивав процес і API Gateway віддавав **502 на кожній сторінці**, не лише на тій, якій бракувало файлу. Тепер переклади й дані читаються з бандла, а `ActivityDataService` завершує потік замість того, щоб віддавати помилку підписникам |
| **Playwright мокає API окремим процесом на `:3000`, а не через `page.route()`** | Застосунок рендерить перший пейнт у Node, а `provideClientHydration()` віддає результат браузеру через transfer cache — браузерний перехоплювач не бачить SSR-запитів і клієнт їх не повторює. Готова відповідь на «як ви тестуєте SSR-застосунок» |

> **Для співбесіди:** інцидент із `sanitize-html` — це готова історія на питання «як ви переконуєтесь, що оновлення бібліотеки нічого не зламало». Патч-реліз, ESM-only транзитивна залежність, 502 на всіх роутах, і в результаті — окремий CI-крок, який це відтворює. Це сильніша відповідь, ніж будь-який опис піраміди тестування.

## 2. P0 — робити першим

### P0-5. Прод-БД відкрита в інтернет

**Факт.** Перевірено на живому AWS **2026-08-27**, не з документа:

```
aws ec2 describe-security-groups --group-ids sg-00490c96bfbce5a7a
→ tcp 5432 ← 194.44.90.247/32, 172.31.0.0/16, 0.0.0.0/0
```

`csd-postgres` (PostgreSQL 16.13, `db.t4g.micro`, `PubliclyAccessible: true`, VPC `vpc-0a6d4906b6fe68974`, subnet group `default`) приймає підключення на 5432 **з будь-якої адреси в інтернеті**. Два вужчі CIDR повністю поглинуті третім і не обмежують нічого — вони створюють хибне враження, що доступ звужений.

**Чому так вийшло — це не недбалість, а наслідок архітектури.** У `backend/serverless.yml` немає секції `vpc`, тобто Lambda працює **поза VPC** і ходить у RDS публічним ендпоїнтом з динамічних AWS-адрес. Плюс `deploy.yml` виконує `migration:show` / `migration:run` з GitHub-раннера, чий IP теж динамічний. За такої конструкції звузити правило нема до чого: allowlist GitHub Actions — це тисячі CIDR при ліміті 60 правил на security group.

**Що саме під загрозою.** Не абстрактні «дані»:

| Таблиця | Вміст |
|---|---|
| `complaints` | скарги з категоріями `corruption` і `staff_behavior` — тобто **PSEA/fraud-механізм**: текст звернення, телефон і email заявника (`complaint.entity.ts`) |
| `inquiries`, `recovery_forms`, `winterization_forms` | ПІБ, телефони, email, локації заявників на допомогу |
| `users` | хеші паролів адміністраторів |

Для організації, яка тримає механізм повідомлення про зловживання, витік `complaints` — це не інцидент із даними, а питання безпеки людей, які цим механізмом скористались. Саме тому пункт стоїть **вище за P0-3**: ціна помилки там — сліпа регресія у фронтенді, тут — треті особи в базі зі скаргами.

**Наскільки це реально.**

- PostgreSQL не має вбудованого обмеження швидкості невдалих логінів — брутфорс стримується тільки пропускною здатністю мережі.
- Відкритий 5432 на публічному RDS-ендпоїнті знаходять **масові сканери**, а не таргетовані атаки. Це фоновий трафік, питання годин.
- Будь-яка майбутня CVE в PostgreSQL з authentication bypass або RCE стає інтернет-досяжною в день публікації, а не після компрометації периметра.
- `src/database/data-source.ts:18-21` вмикає TLS у проді як `{ rejectUnauthorized: false }`. Трафік шифрується, але **сертифікат сервера не перевіряється** — захисту від активного MITM немає, лише від пасивного прослуховування.

**Варіанти повного закриття.** У всіх трьох Lambda переїжджає у VPC, а RDS стає приватною. Різниця — чим забезпечити вихід у інтернет, який бекенду потрібен для Cloudflare Turnstile (`turnstile.guard.ts:21` → `https://challenges.cloudflare.com/turnstile/v0/siteverify`). S3 закривається безкоштовним gateway-endpoint, Turnstile — ні.

| | Варіант | Ціна / міс | Зусилля | Застереження |
|---|---|---|---|---|
| **A** | NAT Gateway | **~$38** ($0.052/год × 730) + $0.052/ГБ | 1–2 дні | Найпростіше й найнадійніше. Майже подвоює поточний рахунок ($20–30) |
| **B** | NAT-інстанс `t4g.nano` | **~$3–4** | 1–2 дні + підтримка | Патчі, моніторинг і single point of failure стають твоєю відповідальністю |
| **C** | Dual-stack VPC + egress-only IGW (IPv6) | **$0** за шлюз | 1–2 дні + невизначеність | `challenges.cloudflare.com` має AAAA-записи, шлюз безкоштовний. Але потрібні dual-stack підмережі й контроль порядку DNS-резолву в Node — менш ходжений шлях, закладай час на розбирання |

**Спільний наслідок A–C, який легко проґавити:** після переїзду міграції з GitHub-раннера перестануть діставати БД. Потрібен окремий шлях — маленька «міграційна» Lambda у тій самій VPC, яку викликає воркфлоу (~0.5 дня), або self-hosted runner. Це не опція, а частина роботи.

**Що зробити зараз — години, без зміни архітектури.** Мережеву експозицію це не прибирає, але прибирає найдешевші шляхи її використати:

1. ~~`rds.force_ssl`~~ — **перевірено 2026-08-27: `default.postgres16` має `rds.force_ssl = 1`**, сервер відхиляє нешифровані підключення. Половина TLS-питання вже закрита; друга половина — пункт 2.

Якщо бандл не читається — застосунок **падає на старті** замість тихого відкату до неперевіреного з'єднання (та сама політика, що в `assert-required-env.ts`). ## 3. P1 — цього місяця

### P1-2. JWT у `localStorage`

**Факт.** `ui` зберігає JWT у `localStorage`. Читачів **шість**, не один:

| Файл | Як читає |
|---|---|
| `core/services/auth.service.ts` | `set` / `get` / `remove` — легітимний власник ключа |
| `core/interceptors/auth.interceptor.ts` | `getItem('token')` для Angular `HttpClient` |
| `features/admin/wash-forms-list/wash-forms-list.ts:751` | **сирий `fetch()` з `Authorization: Bearer ${token}` вручну** |
| `features/admin/complaints/complaints-list.ts:795` | те саме |
| `features/admin/inquiries/inquiries-list.ts:728` | те саме |
| `features/admin/winterization-forms-list/winterization-forms-list.ts:881` | те саме |
| `features/admin/recovery-forms-list/recovery-forms-list.ts:803` | те саме |

Пʼять адмінських компонентів роблять експорт XLSX через нативний `fetch()` в обхід і `AuthService`, і `authInterceptor` — бо `HttpClient` незручний для blob-завантаження. Кожен ліпить заголовок авторизації самостійно.

**Наслідок для оцінки.** Це **не** «поміняти два місця». Перенесення токена в памʼять зачіпає сім файлів, і пʼять із них треба спершу привести до одного шляху (сервіс експорту з `HttpClient` + `responseType: 'blob'`, або спільний хелпер), інакше рефакторинг доведеться робити пʼять разів. **Оцінку піднято з 1–2 днів до 2–3.**

Побічна проблема тієї ж природи: обробка 401 продубльована в пʼяти місцях і вже розходиться (там `alert()`, в інтерсепторі — інша логіка).

**Ризик.** `localStorage` доступний будь-якому JS на сторінці. Один XSS — і токен витікає. `httpOnly`-кука цього не дозволяє.

**Що зробити (за зростанням вартості):**

1. **Мінімум сьогодні:** застосувати CSP (див. P1-3) — це знижує ймовірність XSS.
2. **Правильно:** access-токен тримати **в памʼяті** (сигнал/змінна, гине при перезавантаженні), refresh — в `httpOnly; Secure; SameSite=Strict; Path=/api/auth/refresh` куці. Refresh у БД зберігати **хешем**, ротувати при кожному використанні, детектувати повторне використання.
3. Врахувати SSR: `localStorage` не існує на сервері — перевірити, що `authInterceptor` і сервіси не звертаються до нього під час серверного рендерингу.

Це не «зробити ідеально» — це усунути найдешевший шлях до захоплення адмінської сесії.

### P1-3. CSP спроєктована, але не застосована

`infra/SECURITY-HEADERS.md` містить готовий allowlist і runbook. Статус — **не застосовано**.

Порядок безпечного впровадження: `Content-Security-Policy-Report-Only` → зібрати порушення (Leaflet із CDN, інлайнові стилі Angular, Turnstile) → уточнити allowlist → перевести в enforce. Півдня роботи, і це найдешевший захист від наслідків P1-2.

**Дрібниця, яка виявилась при вимірюванні прода 2026-09-02:** `index.html` тягне з `unpkg.com` три CSS і два JS Leaflet, і атрибут `integrity` стоїть лише на `leaflet.css`. Решта — без SRI. Це та сама поверхня, яку закриває CSP, тож логічно робити одним заходом.

**Staging свідомо без CSP.** Заголовки на staging віддає окрема response-headers policy `csd-frontend-security-headers-staging` — прод-набір плюс `X-Robots-Tag: noindex, nofollow`, але без CSP: інакше staging почав би ловити порушення, яких немає в проді, і перевірка перестала б щось означати.

### P1-4. Одна e2e-спека на 16 контролерів

`backend/test/` містить `app.e2e-spec.ts` — одну спеку. Контролерів у `backend/src` — 16, сутностей — 29.

Інфраструктура вже є і вона хороша: `test-app.factory.ts`, `factories/`, `setup-pg.ts` / `teardown-pg.ts`, Testcontainers. **Вартість додавання нової e2e-спеки — низька.** Нарощувати по одній на модуль, починаючи з тих, де є гроші й персональні дані: needs-форми, завантаження в `csd-media-private`, auth.

## 4. P2 — коли дійдуть руки

**Дрейф версій Postgres.** Локально 14 (Homebrew), e2e `postgres:16-alpine`, прод 16.13. Міграції пишуться на 14 і застосовуються на 16. Виправлення тривіальне — підняти локальний dev на 16, щоб усі три збіглися.

> **2026-08-27:** повний набір із 14 міграцій уперше застосовано до справжньої 16.13 — staging-RDS `csd-postgres-staging`. Усі 14 пройшли без помилок. Це знижує гостроту пункту, але **не закриває** його: перевірено поточний набір, а не майбутні міграції. Тепер staging і є місцем, де кожна нова міграція зустрічає 16.13 раніше за прод.

**Головна сторінка везе 75 KB блогу в transfer cache.** Виміряно на живому `www.csd-fund.org` 2026-09-02: `<script id="ng-state">` — 91 628 B, з них 75 566 B це відповідь на `GET /api/blog?page=1&limit=10`, ще 4 424 B — `/api/blog/featured`, решта — анотації гідратації. Після PR #163 це найбільший окремий шматок HTML головної. Питання не в кеші, а в ліміті: якщо сторінка рендерить менше десяти карток, зменшення `limit` зрізає цей запис напряму. Виносити запис із transfer cache через `withHttpTransferCacheOptions({ filter })` — гірша угода: HTML стане менший, але клієнт піде по ці дані в API-Lambda, з холодним стартом включно.

**`format:check` в `ui` покриває тільки SCSS.** `"format:check": "prettier --check \"src/**/*.scss\""` — тобто `verify` **ніколи** не перевіряє форматування `.ts` і `.html`, хоча `format` їх форматує. Розширити glob до `src/**/*.{ts,html,scss}`.

**`lint` у бекенді несе `--fix`.** Це не баг, але пастка: `npm run lint` мовчки переписує файли. У CI використовується правильний `lint:check` — але людині, яка запускає `lint` локально перед комітом, варто про це памʼятати.

**Observability.** Немає `pg_stat_statements`, немає алертів на помилки Lambda, немає структурованих логів. Мінімум: увімкнути `pg_stat_statements` на RDS (parameter group + `shared_preload_libraries`), додати CloudWatch alarm на `Errors` і `Duration p99` обох Lambda, і алерт на `age(backend_xmin)` для БД.

**Інфраструктура застосовується руками.** `infra/` — CloudFront headers policy, S3 CORS. Бакет `csd-media-private` створено вручну, не Serverless. Це працює, але не відтворюється: якщо акаунт доведеться перестворити, частина конфігурації існує лише в консолі AWS. Мінімум — тримати JSON-и в репозиторії з командою застосування (це вже частково зроблено).

**Немає rate limiting.** Публічні ендпоїнти форм захищені Turnstile, але не лімітом запитів. При зловживанні — рахунок за Lambda і RDS.

## 5. Як користуватись цим документом

- Пункт закритий → **видалити з тіла документа**, а не позначати `~~закреслено~~`. Закритий пункт переїжджає одним рядком у блок «Закрито з моменту попередньої ревізії» в §0 **із SHA коміта, який його закрив**.
- **Цей файл відстежується git** (раніше був у `.gitignore`, знято разом із PR staging-середовища). Причина зміни: репозиторій має два робочі клони, а ігнорований файл існує в кожному окремо — дві копії тихо розходились, тобто ламалось саме те, від чого застерігає цей розділ. Тепер видалений пункт відновлюється з історії, а не тільки з рядка в §0.
- SHA закриваючого коміта відомий лише **після** коміту. Тому рядок у §0 пишеться у два такти: спершу номер PR, потім SHA.
- Цей блок **не накопичується**: при наступній ревізії шапки попередній вміст блока видаляється, лишається тільки закрите з того часу.
- Номери **не перевикористовувати** і не перенумеровувати (див. шапку).
- Знайшов нову проблему → додати з **пріоритетом і оцінкою**, інакше список перетвориться на звалище.
- **Жоден пункт не є авторитетнішим за код.** Розійшлось — відкрити `.ts`/`.yml`, виправити документ у тій самій зміні і оновити коміт у шапці.
- Перед тим як щось із P0 закривати — переконатись, що це досі актуально: `test.yml` міг змінитись.
